# Runbook — Phase 2 Comment cutover and rollback

Operator procedure for moving `comments` from the monolith (`dev.db`) to `comment-service`
(`comment-service/comment.db`, port 8082). It follows
[`phases/phase-2-comment.md`](../phases/phase-2-comment.md) §2.2/§4/§6 and
[`05-data-sync-and-rollback-design.md`](../05-data-sync-and-rollback-design.md) §3–§6, using the
flag names of [`04-strangler-wiring-design.md`](../04-strangler-wiring-design.md) §1.1 and the
`favorite-sync` CLI with `--domain comment` (see
[`tools/favorite-sync`](../../../tools/favorite-sync/README.md)). The structure mirrors
[`phase-1-favorite-cutover.md`](phase-1-favorite-cutover.md); differences specific to Comment are
marked **Comment:**.

What differs from Favorite (05 §1.2, §3):

- Natural key is the comment `id` (UUID generated by the monolith's `io.spring.core.comment.Comment`
  and passed to the service on dual-write, so both sides hold identical rows).
- The row has a payload (`body, article_id, user_id, created_at, updated_at`), so reconcile reports
  a **`diverged`** bucket in addition to `missing`/`extra`. Comments cannot be edited in Conduit,
  so `diverged>0` always means a dual-write bug or a manual edit, never normal traffic.
- Timestamps are copied as the raw stored SQLite value (INTEGER millis from `DateTimeHandler`,
  TEXT from `V2__seed_data.sql`), never reformatted, so `GET /articles/{slug}/comments` and the
  GraphQL `DateTimeCursor` (millis) are byte-identical whichever side serves them.
- No FK constraints: `comments` can be backfilled and rolled back independently of `articles` and
  `users`; orphan comments of deleted articles exist on both sides and are **not** drift.

## 0. Prerequisites

| Item | Check |
|---|---|
| JDK 11 | `java -version` → 11.x (`export JAVA_HOME=...`) |
| CLI built | `cd tools/favorite-sync && ./gradlew installDist` → `build/install/favorite-sync/bin/favorite-sync`; below aliased as `favorite-sync` |
| Service schema | `comment-service` has been started at least once against `comment-service/comment.db` so its Flyway `V1__create_comment_tables.sql` created `comments` (the CLI refuses to run otherwise: `table 'comments' is missing in comment-service/comment.db`) |
| Service healthy | `curl -s http://localhost:8082/actuator/health` → `{"status":"UP"}` |
| Shared JWT secret | monolith and service use the same `JWT_SECRET` |
| Baseline | monolith `./gradlew build -x jacocoTestCoverageVerification` green, all flags at defaults (`extraction.comment.enabled=false`); Phase 1 Favorite may be in any state — the flags are independent |
| Reports dir | `mkdir -p build/reconcile/comment` |
| Paths | run the CLI from the repo root so `dev.db` and `comment-service/comment.db` resolve as written below |

Flags are set as env vars (Spring relaxed binding) and take effect on (rolling) restart, e.g.
`EXTRACTION_COMMENT_ENABLED=true EXTRACTION_COMMENT_WRITE=dual-write`. If the optional runtime
flip endpoint (04 §1.3 b) is deployed, the same key/value pairs are POSTed instead.

State reference (05 §5):

| State | `extraction.comment.enabled` | `.write` | `.read` | Authority |
|---|---|---|---|---|
| Off (today) | `false` | – | – | monolith |
| A. Shadow-write | `true` | `dual-write` | `monolith` | monolith |
| A'. Shadow-read | `true` | `dual-write` | `shadow` | monolith |
| B. Parallel read | `true` | `dual-write` | `extracted` | monolith |
| C. Service authoritative | `true` | `extracted` | `extracted` | **service** |

## 1. Enter state A — enable dual-write

```sh
EXTRACTION_COMMENT_ENABLED=true \
EXTRACTION_COMMENT_WRITE=dual-write \
EXTRACTION_COMMENT_READ=monolith \
EXTRACTION_COMMENT_BASE_URL=http://localhost:8082 \
EXTRACTION_COMMENT_FALLBACK=monolith \
  <restart monolith>
```

Verify: post a comment through the public API and confirm the row appears in **both** files with
the same `id`, `body`, `article_id`, `user_id` and `created_at`.

```sh
curl -s -X POST -H "Authorization: Token $JWT" -H 'Content-Type: application/json' \
  -d '{"comment":{"body":"dual-write check"}}' localhost:8080/articles/<slug>/comments | jq .comment.id   # <uuid>
```

Expected: `201`, and the `POST /internal/articles/{articleId}/comments` call is visible in the
service log with the *same* `id` and `createdAt` (the monolith generates both — phase-2 §2.1).
Then `DELETE /articles/<slug>/comments/<uuid>` → `204` and the row disappears on both sides.
Mirror failures must appear only as WARN + outbox rows; the user request stays 2xx.

## 2. Record T0 and backfill (05 §3)

Dual-write must already be on (step 1) so comments written after T0 arrive via the mirror.

```sh
favorite-sync backfill --domain comment --source dev.db --target comment-service/comment.db --chunk 5000 \
  | tee build/reconcile/comment/backfill.log
```

Expected output (counts will differ):

```
backfill domain=comment table=comments source=dev.db target=comment-service/comment.db chunk=5000
backfill T0=2026-09-03T04:00:00.123Z
backfill snapshot=/tmp/favorite-sync-snapshot-....db
backfill sourceRows=4213 targetRowsBefore=0
backfill chunk=1 rows=4213 inserted=4213 skipped=0 lastKey=ffe0...
backfill done rowsRead=4213 rowsInserted=4213 rowsSkipped=0 chunks=1 targetRowsAfter=4213 T0=2026-09-03T04:00:00.123Z
```

Record **T0** in the change ticket. The walk is keyset-paginated by `id`; `rowsSkipped > 0` is
normal when dual-write already mirrored rows or the job is re-run after an interruption — simply
re-run the same command until it finishes; it is idempotent (`INSERT OR IGNORE`, existing target
rows are never overwritten). Exit code must be `0`.

**Comment:** spot-check one seed row and one application-written row after the backfill; both
must show the identical stored `created_at` on each side (the seed rows are TEXT
`YYYY-MM-DD HH:MM:SS`, application rows are INTEGER millis):

```sh
sqlite3 dev.db "select id, typeof(created_at), created_at from comments order by id limit 3"
sqlite3 comment-service/comment.db "select id, typeof(created_at), created_at from comments order by id limit 3"
```

(If `sqlite3` is not installed, `favorite-sync reconcile` in step 3 performs the same check for
every row — a storage-class difference shows up as `diverged` with `columns: ["created_at"]`.)

## 3. Reconcile to zero drift, N times (05 §4, §5.1)

Report-only run immediately after the backfill:

```sh
favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db \
  --report build/reconcile/comment/$(date -u +%Y%m%dT%H%M%SZ).json; echo exit=$?
```

Expected:

```
reconcile domain=comment table=comments phase=before monolith=4213 service=4213 missing=0 extra=0 diverged=0 status=CLEAN
reconcile report=build/reconcile/comment/20260903T040500Z.json
exit=0
```

- `exit=1` with `missing>0`: comments posted after the snapshot whose mirror failed, or a mirror
  bug. Wait for the outbox to drain and re-run. If it persists, repair toward the monolith:
  ```sh
  favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --repair to-target \
    --report build/reconcile/comment/repair-$(date -u +%Y%m%dT%H%M%SZ).json
  ```
  Expected: `reconcile repair=to-target inserted=<n> deleted=0 updated=<m> ...`, then a
  `phase=after ... status=CLEAN` line, `exit=0`.
- `extra>0`: comment deletes whose DELETE mirror failed (or rows only the service has). Investigate
  the `id`s listed in the report; if the monolith is right, add `--delete-extras` to the repair.
  The tool **never deletes** without that flag.
- **Comment:** `diverged>0`: the report lists each `id` with the differing `columns`. `body`
  differing means the dual-write sent a different body than it stored locally (bug — stop and
  fix); `created_at`/`updated_at` differing usually means one side reformatted the timestamp
  (check the service's type handler). `--repair to-target` overwrites the whole row from the
  monolith. Never repair a `diverged` row without recording the pre-repair JSON report.
- `exit=2` and `repair would touch N rows, above --max-repair`: mass drift — dual-write is broken.
  Do not override the guard; fix the mirror, then re-run backfill (step 2) and reconcile.

Schedule the report-only command hourly (cron/CI; exit code 1 = alert). The cutover criterion of
05 §5.2 is **N = 7 consecutive days** of `status=CLEAN` (minimum defensible N = 3). Keep every
JSON report — the one-line summaries are the audit trail.

## 4. Enter state A' — `read=shadow`

Entry criteria (05 §5.1 items 1–2): step 3 clean, dual-write running ≥ 24 h with outbox lag ≈ 0.

```sh
EXTRACTION_COMMENT_READ=shadow <restart monolith>
```

Reads are still served by the monolith; the remote adapter is called asynchronously and diffed
(04 §5). Monitor `extraction.shadow.mismatch` and the WARN diff logs on
`GET /articles/{slug}/comments`, `POST /articles/{slug}/comments`,
`DELETE /articles/{slug}/comments/{id}` and the GraphQL `comments` connection (with and without
`first/after`/`last/before` cursors — the `DateTimeCursor` millis must match exactly).

**Comment:** the diff compares the composed `CommentData` (`id, body, createdAt, updatedAt,
author{...}`); profiles are still joined locally, so any mismatch is in the comment row itself and
must correlate with a `diverged`/`missing` entry in the hourly report.

Exit criterion: ≥ 99.99 % agreement over ≥ 24 h with every mismatch explained (typically an
in-flight dual-write). Keep hourly reconciliation running.

## 5. Enter state B — `read=extracted`

```sh
EXTRACTION_COMMENT_READ=extracted <restart monolith>   # fallback stays 'monolith'
```

Verify:

```sh
curl -s localhost:8080/articles/<slug>/comments | jq '.comments | length'        # same as before the flip, never null
curl -s localhost:8080/articles/<slug>/comments | jq '.comments[0] | .createdAt == .updatedAt'   # true (TransferData quirk)
favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db; echo exit=$?   # exit=0
```

Stop the service briefly and confirm `GET /articles/{slug}/comments` still returns 200 served by
the fallback (`extraction.comment.fallback=monolith`). Restart the service.

**Rollback from A/A'/B is a single flag** (05 §6.1, phase-2 §6.1): `EXTRACTION_COMMENT_ENABLED=false`
(or `EXTRACTION_COMMENT_READ=monolith` to keep dual-write warm). No data work is needed — every
write landed in `dev.db` first.

## 6. Cutover to state C — service authoritative (05 §5.2, §5.3)

Entry criteria: N days of `CLEAN` (step 3), zero dead-lettered outbox rows, the rollback drill
(§8) executed once in a non-production environment, an owner on call.

```sh
favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db; echo exit=$?   # must be 0 right before the flip
EXTRACTION_COMMENT_WRITE=extracted <restart monolith>
date -u +%Y-%m-%dT%H:%M:%SZ   # record T_flip
```

From now on writes go only to the service; `dev.db.comments` is a read-replica kept warm by the
service's reverse mirror (if implemented) — otherwise it starts to fall behind and the rollback
below relies entirely on `reverse-backfill`. Continue hourly reconciliation, now labelled:

```sh
favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --authoritative service \
  --report build/reconcile/comment/$(date -u +%Y%m%dT%H%M%SZ).json
```

With `--authoritative service` the interesting buckets are `extraInService` (= comments the
monolith replica is missing) and `diverged`. To keep the replica warm without a reverse mirror,
run periodically:

```sh
favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --authoritative service --repair to-source
```

The monolith table is dropped only after ≥ 30 days without rollback, via a new Flyway migration
(`V3__drop_comments.sql`) — separate approval. Until then the monolith's authorization check
(`AuthorizationService.canWriteComment`) keeps running in the monolith (phase-2 §2.1).

## 7. Rollback from state C (05 §6.2, phase-2 §6.3)

1. Pause comment writes for the flip duration if possible (a comment posted between the flip and
   the reverse-backfill is still recovered by step 3, but a delete is not — see step 4).
2. Flip back to monolith-first:
   ```sh
   EXTRACTION_COMMENT_WRITE=dual-write EXTRACTION_COMMENT_READ=monolith <restart monolith>
   ```
   (or `EXTRACTION_COMMENT_ENABLED=false` to go fully local; `dual-write` keeps a retry cheap).
3. Reverse-backfill by `id` the authority-flip window — copies every comment that exists only in
   the service into the monolith with its stored timestamps, leaves monolith rows untouched:
   ```sh
   favorite-sync reverse-backfill --domain comment --source dev.db --target comment-service/comment.db \
     | tee build/reconcile/comment/reverse-backfill.log
   ```
   Expected:
   ```
   reverse-backfill: copying comment-service/comment.db -> dev.db
   backfill domain=comment table=comments source=comment-service/comment.db target=dev.db chunk=5000
   backfill sourceRows=4390 targetRowsBefore=4213
   backfill done rowsRead=4390 rowsInserted=177 rowsSkipped=4213 chunks=1 targetRowsAfter=4390 T0=...
   ```
   `rowsInserted` is the size of the window that the reverse mirror had not delivered.
4. Verify: zero missing-in-monolith and zero diverged.
   ```sh
   favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --authoritative service \
     --report build/reconcile/comment/rollback-$(date -u +%Y%m%dT%H%M%SZ).json; echo exit=$?
   ```
   Expected: `extra=0 diverged=0` (nothing the service has that the monolith lacks or stores
   differently). `missing>0` means the monolith holds comments the service does not — deletes
   executed in state C whose delete did not reach the monolith. Decide per `id` from the report;
   to apply the service's view of those deletes use
   `--repair to-source --delete-extras` (with `--authoritative service` this deletes the
   monolith-only rows). `diverged>0` here is a defect in the service's persistence of the
   window's rows; `--repair to-source` overwrites the monolith copy from the service.
5. Because there are no FK constraints (05 §1.2, phase-2 §6.4) nothing else in `dev.db` is
   affected; `articles`/`users` need no work.

## 8. Rollback drill (05 §6.4) — run once per environment before step 6

Use copies of the databases, never production files.

```sh
cp dev.db drill-dev.db && cp comment-service/comment.db drill-comment.db
```

| # | Action | Command / flag | Assert |
|---|---|---|---|
| 1 | Reach state B | steps 1, 2, 3, 5 above on the drill DBs | `reconcile --domain comment ... ; echo exit=$?` → `0` |
| 2 | Kill the service mid-traffic; post/delete comments via REST | `kill <comment-service pid>`; `curl -X POST .../comments`, `curl -X DELETE .../comments/<id>` | every request `201`/`204`; rows present/absent in `drill-dev.db` |
| 3 | Restart the service, let the outbox drain | — | `favorite-sync reconcile --domain comment --source drill-dev.db --target drill-comment.db` → `status=CLEAN`, `exit=0` (use `--repair to-target [--delete-extras]` once if the outbox dead-lettered) |
| 4 | Flip to state C and generate writes | `EXTRACTION_COMMENT_WRITE=extracted`; post several comments, delete one pre-existing comment | `reconcile --domain comment ... --authoritative service` shows `extra>0` (service-only rows) and `missing=1` |
| 5 | Execute §7 | `EXTRACTION_COMMENT_WRITE=dual-write`; `favorite-sync reverse-backfill --domain comment --source drill-dev.db --target drill-comment.db` | `rowsInserted` = number of comments posted in step 4 |
| 6 | Verify | `favorite-sync reconcile --domain comment --source drill-dev.db --target drill-comment.db --authoritative service; echo exit=$?` | `extra=0 diverged=0`; `missing=1` is the step-4 delete — apply with `--repair to-source --delete-extras`, then `exit=0` |
| 7 | **Comment:** timestamp round-trip | `curl localhost:8080/articles/<slug>/comments` for a comment posted in step 4 with `read=monolith` | `createdAt` identical to the value the service returned in state C |

Record the seven results (with the JSON reports) in the change ticket; this is entry criterion 3
of 05 §5.2.

## 9. Quick reference

| Situation | Command |
|---|---|
| Hourly drift check (alert on exit 1) | `favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --report build/reconcile/comment/$(date -u +%Y%m%dT%H%M%SZ).json` |
| Service missing or diverged rows (states A/B) | `favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --repair to-target` |
| Service has stale rows the monolith deleted (states A/B) | `favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --repair to-target --delete-extras` |
| Rebuild service DB from scratch (states A/B) | stop service, delete `comment-service/comment.db`, start service (Flyway), `favorite-sync backfill --domain comment --source dev.db --target comment-service/comment.db`, then `reconcile --domain comment ...` |
| Rollback from A/A'/B | `EXTRACTION_COMMENT_ENABLED=false` — no data work |
| Rollback from C | `EXTRACTION_COMMENT_WRITE=dual-write`, then `favorite-sync reverse-backfill --domain comment --source dev.db --target comment-service/comment.db`, then `favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --authoritative service` |
| Keep monolith replica warm in state C | `favorite-sync reconcile --domain comment --source dev.db --target comment-service/comment.db --authoritative service --repair to-source` |
| Inspect a reported `diverged` id | `jq '.tables[0].diverged' build/reconcile/comment/<report>.json` → `[{"id":"...","columns":["body"]}]` |

# Runbook — Phase 3 Tag cutover and rollback

Operator procedure for moving `tags` and `article_tags` from the monolith (`dev.db`) to
`article-service` (`article-service/article.db`, port 8083). It follows
[`phases/phase-3-tag.md`](../phases/phase-3-tag.md) §2.1/§2.2/§4/§6 and
[`05-data-sync-and-rollback-design.md`](../05-data-sync-and-rollback-design.md) §3–§6, using the
flag names of [`04-strangler-wiring-design.md`](../04-strangler-wiring-design.md) §1.1 and the
`favorite-sync` CLI with `--domain tag` (see
[`tools/favorite-sync`](../../../tools/favorite-sync/README.md)). The structure mirrors
[`phase-2-comment-cutover.md`](phase-2-comment-cutover.md); differences specific to Tag are marked
**Tag:**.

**`articles` stays in the monolith until Phase 4.** `article-service` owns only `tags` and
`article_tags` in this phase; its `articles` table exists (created by `V1__create_article_tables.sql`)
but stays empty, and nothing in this runbook reads or writes it. `article_tags.article_id`
therefore points at rows that live in another database — that is expected, there are no FKs.

What differs from Comment (05 §1.2, §3):

- **Two tables in one domain.** Every command processes `tags` first and `article_tags` second, in
  a single invocation, and reports each table separately. Tags are copied first so a relation is
  never inserted before the tag row it references.
- `tags` is keyed by `id` (a UUID generated by `io.spring.core.article.Tag` and passed to the
  service on dual-write, so both sides hold the same ids) with `name` as the only payload, so a
  `diverged` bucket can appear for `tags`. `article_tags` is keyed by the pair
  `(article_id, tag_id)` and has no payload: it can only be `missing`/`extra`.
- **No unique constraint anywhere.** `tags.name` is not unique and `article_tags` has no key at
  all. The tool inserts a pair only when it is absent and reports repeated rows as
  `duplicateKeysInMonolith` / `duplicateKeysInService` — duplicates are **not** drift and are never
  removed by a repair. Removing them would change `GET /tags` (which is
  `select name from tags`, no `DISTINCT`) and the `tagList` cardinality.
- **Tags are written only on article create** (`MyBatisArticleRepository.createNew`); article
  update and delete never touch `tags`/`article_tags`. A tag with no articles, or a relation whose
  article was deleted, is normal state on both sides and must never be "cleaned up".

## 0. Prerequisites

| Item | Check |
|---|---|
| JDK 11 | `java -version` → 11.x (`export JAVA_HOME=...`) |
| CLI built | `cd tools/favorite-sync && ./gradlew installDist` → `build/install/favorite-sync/bin/favorite-sync`; below aliased as `favorite-sync` |
| Service schema | `article-service` has been started at least once against `article-service/article.db` so its Flyway `V1__create_article_tables.sql` created `tags` and `article_tags` (the CLI refuses to run otherwise: `table 'article_tags' is missing in article-service/article.db`) |
| Service healthy | `curl -s http://localhost:8083/actuator/health` → `{"status":"UP"}` |
| Shared JWT secret | monolith and service use the same `JWT_SECRET` |
| Baseline | monolith `./gradlew build -x jacocoTestCoverageVerification` green, all flags at defaults (`extraction.tag.enabled=false`); Phases 1 and 2 may be in any state — the flags are independent |
| Reports dir | `mkdir -p build/reconcile/tag` |
| Paths | run the CLI from the repo root so `dev.db` and `article-service/article.db` resolve as written below |

Flags are set as env vars (Spring relaxed binding) and take effect on (rolling) restart, e.g.
`EXTRACTION_TAG_ENABLED=true EXTRACTION_TAG_WRITE=dual-write`. If the optional runtime flip
endpoint (04 §1.3 b) is deployed, the same key/value pairs are POSTed instead.

State reference (05 §5):

| State | `extraction.tag.enabled` | `.write` | `.read` | Authority |
|---|---|---|---|---|
| Off (today) | `false` | – | – | monolith |
| A. Shadow-write | `true` | `dual-write` | `monolith` | monolith |
| A'. Shadow-read | `true` | `dual-write` | `shadow` | monolith |
| B. Parallel read | `true` | `dual-write` | `extracted` | monolith |
| C. Service authoritative | `true` | `extracted` | `extracted` | **service** |

## 1. Enter state A — enable dual-write

```sh
EXTRACTION_TAG_ENABLED=true \
EXTRACTION_TAG_WRITE=dual-write \
EXTRACTION_TAG_READ=monolith \
EXTRACTION_TAG_BASE_URL=http://localhost:8083 \
EXTRACTION_TAG_FALLBACK=monolith \
  <restart monolith>
```

Verify: create an article with a new tag and a pre-existing tag, and confirm both sides hold the
same rows with the same tag ids.

```sh
curl -s -X POST -H "Authorization: Token $JWT" -H 'Content-Type: application/json' \
  -d '{"article":{"title":"dual-write check","description":"d","body":"b","tagList":["java","brand-new-tag"]}}' \
  localhost:8080/articles | jq '.article.tagList'
```

Expected: `201`, the `PUT /internal/articles/{articleId}/tags` call visible in the service log with
the *same* tag ids the monolith generated (phase-3 §2.1), `brand-new-tag` inserted into `tags` on
both sides, and `java` reused on both sides rather than duplicated. Mirror failures must appear
only as WARN + outbox rows; the user request stays 2xx.

**Tag:** article update and delete produce no tag traffic at all — that is correct, not a missed
mirror.

## 2. Record T0 and backfill (05 §3)

Dual-write must already be on (step 1) so tags written after T0 arrive via the mirror.

```sh
favorite-sync backfill --domain tag --source dev.db --target article-service/article.db --chunk 5000 \
  | tee build/reconcile/tag/backfill.log
```

Expected output (counts will differ):

```
backfill domain=tag table=tags source=dev.db target=article-service/article.db chunk=5000
backfill T0=2026-09-03T04:00:00.123Z
backfill snapshot=/tmp/favorite-sync-snapshot-....db
backfill sourceRows=812 targetRowsBefore=0
backfill chunk=1 rows=812 inserted=812 skipped=0 lastKey=ffe0...
backfill done rowsRead=812 rowsInserted=812 rowsSkipped=0 chunks=1 targetRowsAfter=812 T0=2026-09-03T04:00:00.123Z table=tags
backfill domain=tag table=article_tags source=dev.db target=article-service/article.db chunk=5000
backfill sourceRows=3907 targetRowsBefore=0
backfill chunk=1 rows=3907 inserted=3906 skipped=1 lastKey=article-99|ffe0...
backfill done rowsRead=3907 rowsInserted=3906 rowsSkipped=1 chunks=1 targetRowsAfter=3906 T0=... table=article_tags
backfill done domain=tag tables=2 rowsRead=4719 rowsInserted=4718 rowsSkipped=1 chunks=2 T0=2026-09-03T04:00:00.123Z
```

Record **T0** in the change ticket. Both tables come from the *same* snapshot, so the two tables
are consistent with each other even if the monolith keeps writing. The walk is keyset-paginated by
`id` for `tags` and by `(article_id, tag_id)` for `article_tags`. Exit code must be `0`.

`rowsSkipped > 0` is normal when dual-write already mirrored rows, when the job is re-run after an
interruption, or — **Tag:** — when the monolith holds the same `(article_id, tag_id)` pair twice:
the target stores the pair once and the surplus source rows count as skipped. Re-run the command
until it finishes; it is idempotent and never multiplies pairs.

Spot-check that `GET /tags` ordering is preserved (the service must return `select name from tags`
order, duplicates included):

```sh
sqlite3 dev.db "select name from tags limit 5"
curl -s localhost:8083/internal/tags | jq '.tags[:5]'
```

## 3. Reconcile to zero drift, N times (05 §4, §5.1)

Report-only run immediately after the backfill:

```sh
favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db \
  --report build/reconcile/tag/$(date -u +%Y%m%dT%H%M%SZ).json; echo exit=$?
```

Expected:

```
reconcile domain=tag table=tags phase=before monolith=812 service=812 missing=0 extra=0 diverged=0 status=CLEAN
reconcile domain=tag table=article_tags phase=before monolith=3907 service=3906 missing=0 extra=0 diverged=0 duplicateKeys=1/0 status=CLEAN
reconcile report=build/reconcile/tag/20260903T040500Z.json
exit=0
```

The JSON report has `"domain":"tag"` and two entries in `tables` (`tags`, then `article_tags`);
`summary.drift`/`summary.clean` count **tables**, `summary.driftRows` sums the rows of both.

- `exit=1` with `missing>0` on `tags`: an article created after the snapshot whose tag mirror
  failed. Wait for the outbox to drain and re-run. If it persists, repair toward the monolith —
  one command fixes both tables, tags first:
  ```sh
  favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --repair to-target \
    --report build/reconcile/tag/repair-$(date -u +%Y%m%dT%H%M%SZ).json
  ```
  Expected: `reconcile repair=to-target inserted=<n> deleted=0 updated=<m> ...`, then two
  `phase=after ... status=CLEAN` lines, `exit=0`.
- `missing>0` on `article_tags` only, with `tags` clean: the tag row was mirrored but the relation
  was not, i.e. a partial `PUT /internal/articles/{id}/tags`. `--repair to-target` inserts the
  missing pairs; the article's `tagList` was wrong in state B until it did.
- `extra>0`: rows only the service has. There is no monolith operation that deletes tags, so this
  is either a manual edit or a stale service DB. Investigate the keys listed in the report; if the
  monolith is right, add `--delete-extras`. The tool **never deletes** without that flag.
- **Tag:** `diverged>0` (only possible on `tags`): the same `id` has a different `name` on each
  side. That is a dual-write bug or a manual edit — Conduit has no rename-tag operation. The
  report lists `{"id":"...","columns":["name"]}`. `--repair to-target` overwrites the name from the
  monolith; record the pre-repair JSON first.
- **Tag:** `duplicateKeys=n/m` is informational, not drift, and does not affect the exit code. A
  growing `duplicateKeysInMonolith` means articles are being created concurrently with the same new
  tag name (`findTag` races `insertTag`); it is pre-existing monolith behaviour.
- `exit=2` and `repair would touch N rows, above --max-repair`: mass drift — dual-write is broken.
  The guard is evaluated over both tables together and nothing is written when it trips. Do not
  override it; fix the mirror, then re-run backfill (step 2) and reconcile.

Schedule the report-only command hourly (cron/CI; exit code 1 = alert). The cutover criterion of
05 §5.2 is **N = 7 consecutive days** of `status=CLEAN` (minimum defensible N = 3). Keep every JSON
report — the one-line summaries are the audit trail.

## 4. Enter state A' — `read=shadow`

Entry criteria (05 §5.1 items 1–2): step 3 clean, dual-write running ≥ 24 h with outbox lag ≈ 0.

```sh
EXTRACTION_TAG_READ=shadow <restart monolith>
```

Reads are still served by the monolith's SQL joins; the remote adapter is called asynchronously and
diffed (04 §5). Monitor `extraction.shadow.mismatch` and the WARN diff logs on `GET /tags`,
`GET /articles?tag=`, `GET /articles/{slug}` (`tagList`) and the GraphQL `tags` datafetcher.

**Tag:** the diff is order-sensitive on purpose — `GET /tags` has no `ORDER BY` and no `DISTINCT`,
and `tagList` follows `article_tags` row order. A mismatch that is only a permutation still means
the service's row order differs from the monolith's and must be fixed before state B; it will not
show up as drift in step 3, which compares sets.

Exit criterion: ≥ 99.99 % agreement over ≥ 24 h with every mismatch explained (typically an
in-flight dual-write). Keep hourly reconciliation running.

## 5. Enter state B — `read=extracted`

```sh
EXTRACTION_TAG_READ=extracted <restart monolith>   # fallback stays 'monolith'
```

Verify:

```sh
curl -s localhost:8080/tags | jq '.tags | length'                       # same as before the flip
curl -s localhost:8080/articles/<slug> | jq '.article.tagList'          # same order as before
curl -s 'localhost:8080/articles?tag=java' | jq '.articlesCount'        # same as before
curl -s 'localhost:8080/articles?tag=does-not-exist' | jq '.articlesCount'   # 0, articles: []
favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db; echo exit=$?   # exit=0
```

An article with no tags must still return `"tagList": []`, never `null`. Stop the service briefly
and confirm `GET /tags` and `GET /articles/{slug}` still return 200 served by the fallback
(`extraction.tag.fallback=monolith`). Restart the service.

**Rollback from A/A'/B is a single flag** (05 §6.1, phase-3 §6.1): `EXTRACTION_TAG_ENABLED=false`
(or `EXTRACTION_TAG_READ=monolith` to keep dual-write warm). No data work is needed — every write
landed in `dev.db` first and the monolith's joins are untouched.

## 6. Cutover to state C — service authoritative (05 §5.2, §5.3)

Entry criteria: N days of `CLEAN` (step 3), zero dead-lettered outbox rows, the rollback drill (§8)
executed once in a non-production environment, an owner on call.

```sh
favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db; echo exit=$?   # must be 0 right before the flip
EXTRACTION_TAG_WRITE=extracted <restart monolith>
date -u +%Y-%m-%dT%H:%M:%SZ   # record T_flip
```

From now on tag writes go only to the service; `dev.db`'s `tags`/`article_tags` become a
read-replica kept warm by the reverse repair below. **The article row itself is still written to
`dev.db` by the monolith** — only its tags live elsewhere, and that stays true until Phase 4.
Continue hourly reconciliation, now labelled:

```sh
favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --authoritative service \
  --report build/reconcile/tag/$(date -u +%Y%m%dT%H%M%SZ).json
```

With `--authoritative service` the interesting buckets are `extraInService` (= rows the monolith
replica is missing) and `diverged`. To keep the replica warm, run periodically:

```sh
favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --authoritative service --repair to-source
```

The monolith tables are dropped only after ≥ 30 days without rollback, via a new Flyway migration —
and not before Phase 4, because `ArticleReadService.xml` still joins them whenever
`extraction.tag.enabled=false`. Separate approval.

## 7. Rollback from state C (05 §6.2, phase-3 §6.2)

1. Pause article creation for the flip duration if possible (an article created between the flip
   and the reverse-backfill is still recovered by step 3).
2. Flip back to monolith-first:
   ```sh
   EXTRACTION_TAG_WRITE=dual-write EXTRACTION_TAG_READ=monolith <restart monolith>
   ```
   (or `EXTRACTION_TAG_ENABLED=false` to go fully local; `dual-write` keeps a retry cheap).
3. Reverse-backfill the authority-flip window — copies every tag and every pair that exists only in
   the service into the monolith, tags first, leaving monolith rows untouched:
   ```sh
   favorite-sync reverse-backfill --domain tag --source dev.db --target article-service/article.db \
     | tee build/reconcile/tag/reverse-backfill.log
   ```
   Expected:
   ```
   reverse-backfill: copying article-service/article.db -> dev.db
   backfill domain=tag table=tags source=article-service/article.db target=dev.db chunk=5000
   backfill done rowsRead=830 rowsInserted=18 rowsSkipped=812 chunks=1 targetRowsAfter=830 T0=... table=tags
   backfill domain=tag table=article_tags source=article-service/article.db target=dev.db chunk=5000
   backfill done rowsRead=3990 rowsInserted=84 rowsSkipped=3906 chunks=1 targetRowsAfter=3991 T0=... table=article_tags
   backfill done domain=tag tables=2 rowsRead=4820 rowsInserted=102 rowsSkipped=4718 chunks=2 T0=...
   ```
   `rowsInserted` is the size of the window that the reverse repair had not delivered. Because
   tags are copied before pairs, the monolith's joins are consistent the moment the command
   finishes.
4. Verify: zero extra-in-service and zero diverged.
   ```sh
   favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --authoritative service \
     --report build/reconcile/tag/rollback-$(date -u +%Y%m%dT%H%M%SZ).json; echo exit=$?
   ```
   Expected: `extra=0 diverged=0` on both tables. `missing>0` means the monolith holds tag rows the
   service does not — normally the replica rows the service never received; since no operation
   deletes tags, prefer keeping them (they are harmless: an unused tag only shows up in
   `GET /tags`). Only if you accept the service's view, use
   `--repair to-source --delete-extras` (with `--authoritative service` this deletes the
   monolith-only rows). `diverged>0` here is a defect in the service's persistence of the window's
   rows; `--repair to-source` overwrites the monolith copy from the service.
5. Because there are no FK constraints (05 §1.2, phase-3 §6.3) nothing else in `dev.db` is
   affected: `article_tags` is rebuilt without touching `articles`, which never left the monolith.
6. Sanity-check the user-visible reads with the flag off:
   ```sh
   EXTRACTION_TAG_ENABLED=false <restart monolith>
   curl -s localhost:8080/tags | jq '.tags | length'
   curl -s localhost:8080/articles/<slug-created-in-state-C> | jq '.article.tagList'
   ```

## 8. Rollback drill (05 §6.4) — run once per environment before step 6

Use copies of the databases, never production files.

```sh
cp dev.db drill-dev.db && cp article-service/article.db drill-article.db
```

| # | Action | Command / flag | Assert |
|---|---|---|---|
| 1 | Reach state B | steps 1, 2, 3, 5 above on the drill DBs | `reconcile --domain tag ... ; echo exit=$?` → `0` |
| 2 | Kill the service mid-traffic; create articles with new and existing tags | `kill <article-service pid>`; `curl -X POST .../articles` | every request `201`; tags + pairs present in `drill-dev.db` |
| 3 | Restart the service, let the outbox drain | — | `favorite-sync reconcile --domain tag --source drill-dev.db --target drill-article.db` → both tables `status=CLEAN`, `exit=0` (use `--repair to-target` once if the outbox dead-lettered) |
| 4 | Flip to state C and generate writes | `EXTRACTION_TAG_WRITE=extracted`; create two articles, one with a brand-new tag | `reconcile --domain tag ... --authoritative service` shows `extra>0` on both tables |
| 5 | Execute §7 | `EXTRACTION_TAG_WRITE=dual-write`; `favorite-sync reverse-backfill --domain tag --source drill-dev.db --target drill-article.db` | `rowsInserted` on `tags` = number of new tag names in step 4; on `article_tags` = number of new pairs |
| 6 | Verify | `favorite-sync reconcile --domain tag --source drill-dev.db --target drill-article.db --authoritative service; echo exit=$?` | `extra=0 diverged=0` on both tables, `exit=0` |
| 7 | **Tag:** read round-trip with the flag off | `EXTRACTION_TAG_ENABLED=false`; `curl localhost:8080/articles/<slug from step 4>` | `tagList` identical to what the service returned in state C, same order |
| 8 | **Tag:** duplicate pairs are not multiplied | run steps 5 and 6 a second time | `rowsInserted=0`, `duplicateKeys` unchanged, `exit=0` |

Record the eight results (with the JSON reports) in the change ticket; this is entry criterion 3 of
05 §5.2.

## 9. Quick reference

| Situation | Command |
|---|---|
| Hourly drift check (alert on exit 1) | `favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --report build/reconcile/tag/$(date -u +%Y%m%dT%H%M%SZ).json` |
| Service missing rows or a diverged tag name (states A/B) | `favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --repair to-target` |
| Service has rows the monolith does not (states A/B) | `favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --repair to-target --delete-extras` |
| Rebuild service DB from scratch (states A/B) | stop service, delete `article-service/article.db`, start service (Flyway), `favorite-sync backfill --domain tag --source dev.db --target article-service/article.db`, then `reconcile --domain tag ...` |
| Rollback from A/A'/B | `EXTRACTION_TAG_ENABLED=false` — no data work |
| Rollback from C | `EXTRACTION_TAG_WRITE=dual-write`, then `favorite-sync reverse-backfill --domain tag --source dev.db --target article-service/article.db`, then `favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --authoritative service` |
| Keep monolith replica warm in state C | `favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --authoritative service --repair to-source` |
| Inspect a reported diverged tag | `jq '.tables[0].diverged' build/reconcile/tag/<report>.json` → `[{"id":"...","columns":["name"]}]` |
| Inspect missing relations | `jq '.tables[1].missingInService' build/reconcile/tag/<report>.json` → `[{"articleId":"...","tagId":"..."}]` |
| Count duplicate pairs | `jq '.tables[1].duplicateKeysInMonolithTotal' build/reconcile/tag/<report>.json` |

# Runbook — Phase 4 Article cutover and rollback

Operator procedure for moving `articles` from the monolith (`dev.db`) to `article-service`
(`article-service/article.db`, port 8083), which already owns `tags` and `article_tags` since
Phase 3. It follows [`phases/phase-4-article.md`](../phases/phase-4-article.md) §2.1/§2.2/§4/§6 and
[`05-data-sync-and-rollback-design.md`](../05-data-sync-and-rollback-design.md) §3–§6, using the
flag names of [`04-strangler-wiring-design.md`](../04-strangler-wiring-design.md) §1.1 and the
`favorite-sync` CLI with `--domain tag` **and** `--domain article` (see
[`tools/favorite-sync`](../../../tools/favorite-sync/README.md)). The structure mirrors
[`phase-3-tag-cutover.md`](phase-3-tag-cutover.md); differences specific to Article are marked
**Article:**.

**Two domains, one service, one database file.** After Phase 4 `article.db` holds `articles`,
`tags` and `article_tags`. The sync tool keeps them as two domains: `--domain tag` (Phase 3,
unchanged) and `--domain article` (only `articles`). Every data step below therefore runs **`tag`
first, then `article`**. The order matters for shadow-read comparison of `tagList`, not for
constraints — there are no FKs anywhere.

What differs from Tag (05 §1.2, §3):

- **Single table, seven payload columns.** `articles` is keyed by `id` (a UUID generated by
  `io.spring.core.article.Article` and passed to the service on dual-write, so both sides hold the
  same ids); `user_id, slug, title, description, body, created_at, updated_at` are compared
  value-for-value **as stored**. Timestamps are INTEGER epoch-millis when written by the
  application and TEXT when written by `V2__seed_data.sql`; the tool copies the raw value and never
  reformats it, so the two seed rows stay TEXT on both sides and compare equal.
- **`slug` is UNIQUE, `id` is the key.** `INSERT OR IGNORE` is idempotent by `id` only. A source
  row whose slug is already held by a *different* id on the target is reported as a **conflict**
  (`uniqueConflictsInService` / `uniqueConflictsInMonolith`, log line `backfill conflict
  table=articles ...`), skipped, and counted as drift until an operator resolves it **by id**
  (phase-4 §6.2). The tool never overwrites the holder and never crashes on the constraint.
- **`updated_at` is not touched by `PUT /articles/{slug}`** (`ArticleMapper.xml#update` quirk).
  Both sides preserve it, so a diverged `updated_at` is a defect, never normal traffic.
- **Comments and favorites reference `article_id` by value only.** `comments.article_id`,
  `article_favorites.article_id` and `article_tags.article_id` have no FK, live in three different
  databases after Phases 1–3, and keep pointing at the same UUIDs whichever side owns `articles`.
  Nothing in this runbook rewrites them, and moving `articles` never invalidates them.
- **Article deletion does not cascade** — not in the monolith (`ArticleMapper.xml#delete`), not in
  the service (`DELETE /internal/articles/{id}`), and not in the sync tool: `--delete-extras`
  removes only the `articles` row. Orphaned comments/favorites/tag pairs are expected state on both
  sides and are never "cleaned up".

## 1. Enter state A — enable dual-write

```sh
EXTRACTION_ARTICLE_ENABLED=true \
EXTRACTION_ARTICLE_WRITE=dual-write \
EXTRACTION_ARTICLE_READ=monolith \
EXTRACTION_ARTICLE_BASE_URL=http://localhost:8083 \
EXTRACTION_ARTICLE_FALLBACK=monolith \
  <restart monolith>
```

Verify: create, update and delete an article and confirm both sides hold the same row.

```sh
curl -s -X POST -H "Authorization: Token $JWT" -H 'Content-Type: application/json' \
  -d '{"article":{"title":"dual-write check","description":"d","body":"b","tagList":["java"]}}' \
  localhost:8080/articles | jq '.article | {slug, createdAt, updatedAt}'
sqlite3 dev.db "select id, slug, typeof(created_at), created_at from articles where slug='dual-write-check'"
sqlite3 article-service/article.db "select id, slug, typeof(created_at), created_at from articles where slug='dual-write-check'"
```

Expected: `201`, the `POST /internal/articles` call visible in the service log with the *same* `id`,
`slug` and timestamps the monolith generated (phase-4 §2.1 — the caller generates them so the rows
are identical), identical `typeof(created_at)` on both sides. Mirror failures must appear only as
WARN + outbox rows; the user request stays 2xx.

**Article:** with the Article write route at `dual-write`/`extracted`, tags travel inside
`POST /internal/articles` and the Phase 3 tag dual-write on article create is superseded
(phase-4 §2.1). `--domain tag` reconcile must still be clean afterwards — if it is not, the
service's `POST /internal/articles` is not writing `tags`/`article_tags` like Phase 3's
`PUT .../tags` did.

Then `PUT /articles/dual-write-check` with a new title: `slug` changes on both sides,
`updated_at` changes on **neither** (quirk to preserve). Then `DELETE /articles/<new slug>`: the
row disappears on both sides; its `article_tags` pair, comments and favorites stay.

## 2. Record T0 and backfill (05 §3) — tag, then article

Dual-write must already be on (step 1) so articles written after T0 arrive via the mirror.

```sh
favorite-sync backfill --domain tag     --source dev.db --target article-service/article.db --chunk 5000 \
  | tee build/reconcile/tag/backfill.log          # Phase 3 tables; rowsInserted≈0 if Tag is already live
favorite-sync backfill --domain article --source dev.db --target article-service/article.db --chunk 5000 \
  | tee build/reconcile/article/backfill.log; echo exit=$?
```

Expected output of the article run (counts will differ):

```
backfill domain=article table=articles source=dev.db target=article-service/article.db chunk=5000
backfill T0=2026-09-03T04:00:00.123Z
backfill snapshot=/tmp/favorite-sync-snapshot-....db
backfill sourceRows=1207 targetRowsBefore=3
backfill chunk=1 rows=1207 inserted=1204 skipped=3 lastKey=ffe0...
backfill done rowsRead=1207 rowsInserted=1204 rowsSkipped=3 chunks=1 targetRowsAfter=1207 T0=2026-09-03T04:00:00.123Z table=articles
exit=0
```

Record **T0** of the *article* run in the change ticket. The walk is keyset-paginated by `id`.
`rowsSkipped > 0` is normal when dual-write already mirrored rows (the 3 above) or when the job is
re-run after an interruption; a crash mid-chunk rolls that chunk back and the next run continues.

**Article:** if the output contains

```
backfill conflict table=articles a1b2... slug=how-to-train-your-dragon held by c0de...
backfill done rowsRead=1207 rowsInserted=1203 rowsSkipped=4 chunks=1 conflicts=1 targetRowsAfter=1206 T0=... table=articles
exit=1
```

the service already holds that slug under a different `id` (a row created directly in the service,
a stale `article.db`, or a title re-used after a delete that was mirrored only on one side). The
source row was **not** copied. Decide by id which article is real:

- the service row is bogus → delete it (`sqlite3 article-service/article.db "delete from articles
  where id='c0de...'"` with the service stopped, or `reconcile --repair to-target --delete-extras`
  in step 3) and re-run the backfill;
- the monolith row is bogus → delete it in `dev.db` the same way (its comments/favorites become
  orphans, which is what the monolith's own `DELETE /articles/{slug}` would have left too);
- both are real → one of them needs a new slug, i.e. a `PUT /articles/{slug}` with a new title
  through the monolith while in state A, then re-run.

Spot-check the seed rows kept their TEXT timestamps:

```sh
sqlite3 dev.db "select typeof(created_at), count(*) from articles group by 1"
sqlite3 article-service/article.db "select typeof(created_at), count(*) from articles group by 1"
```

## 3. Reconcile to zero drift, N times (05 §4, §5.1)

Report-only runs immediately after the backfill, tag first:

```sh
favorite-sync reconcile --domain tag     --source dev.db --target article-service/article.db \
  --report build/reconcile/tag/$(date -u +%Y%m%dT%H%M%SZ).json; echo tag=$?
favorite-sync reconcile --domain article --source dev.db --target article-service/article.db \
  --report build/reconcile/article/$(date -u +%Y%m%dT%H%M%SZ).json; echo article=$?
```

Expected:

```
reconcile domain=article table=articles phase=before monolith=1207 service=1207 missing=0 extra=0 diverged=0 conflicts=0/0 status=CLEAN
reconcile report=build/reconcile/article/20260903T040500Z.json
article=0
```

The JSON report has `"domain":"article"` and one entry in `tables` with the comment-style
`diverged` bucket plus `uniqueConflictsInService`/`uniqueConflictsInMonolith`.

- `exit=1` with `missing>0`: an article created after the snapshot whose mirror failed. Wait for
  the outbox to drain and re-run. If it persists, repair toward the monolith:
  ```sh
  favorite-sync reconcile --domain article --source dev.db --target article-service/article.db --repair to-target \
    --report build/reconcile/article/repair-$(date -u +%Y%m%dT%H%M%SZ).json
  ```
  Expected: `reconcile repair=to-target inserted=<n> deleted=0 updated=<m> ...`, then
  `phase=after ... status=CLEAN`, `exit=0`.
- `extra>0`: rows only the service has — an article deleted in the monolith whose
  `DELETE /internal/articles/{id}` mirror failed, or a manual edit. Investigate the ids listed in
  the report; if the monolith is right, add `--delete-extras`. The tool **never deletes** without
  that flag, and deleting the `articles` row leaves its tag pairs/comments/favorites in place on
  purpose.
- `diverged>0`: same `id`, different payload. The report lists the columns, e.g.
  `{"id":"...","columns":["slug","title"]}` (an update whose mirror failed — `PUT /internal/articles/{id}`
  skips blank fields exactly like the monolith, so a partial mirror shows up here),
  `["updated_at"]` (one side rewrote a column the other never touches — a defect) or
  `["created_at"]` with identical instants (one side stored TEXT, the other INTEGER — a
  serialisation defect in the mirror; the monolith's `DateTimeHandler` reads the two forms
  differently, so this **is** drift). `--repair to-target` overwrites the whole row from the
  monolith; record the pre-repair JSON first.
- **Article:** `conflicts=n/m` (`uniqueConflictsInService`/`InMonolith`): a missing or diverged
  row cannot be written because another id holds its slug on the repaired side. It is already
  counted in `missing`/`diverged`; the conflict entry names the `conflictingId`. A repair skips
  such rows (`reconcile table=articles skipped=N rows whose unique value is held by another key
  ...`) and exits `1`. If the holder is an `extraInService` row, `--repair to-target
  --delete-extras` removes it first and the repair converges in one pass; if the holder exists on
  both sides (a slug *swap*), resolve by id by hand as in step 2 — the tool never guesses.
- `exit=2` and `repair would touch N rows, above --max-repair`: mass drift — dual-write is broken.
  Nothing is written when the guard trips. Do not override it; fix the mirror, then re-run backfill
  (step 2) and reconcile.

Schedule both report-only commands hourly (cron/CI; exit code 1 = alert). The cutover criterion of
05 §5.2 is **N = 7 consecutive days** of `status=CLEAN` on both domains (minimum defensible N = 3).
Keep every JSON report — the one-line summaries are the audit trail.

## 4. Enter state A' — `read=shadow`

Entry criteria (05 §5.1 items 1–2): step 3 clean on `tag` and `article`, dual-write running ≥ 24 h
with outbox lag ≈ 0.

```sh
EXTRACTION_ARTICLE_READ=shadow <restart monolith>
```

Reads are still served by the monolith's SQL; the remote adapter is called asynchronously and
diffed (04 §5). Monitor `extraction.shadow.mismatch` and the WARN diff logs on
`GET /articles/{slug}`, `GET /articles?tag=&author=&favorited=&offset=&limit=`,
`GET /articles/feed`, the GraphQL `articles`/`feed` cursor datafetchers, and the slug→article
lookups made by `ArticleFavoriteApi`/`CommentsApi` (404 + `canWriteArticle`/`canWriteComment`).

**Article:** the diff compares the article *row* (`id, slug, title, description, body, userId,
createdAt, updatedAt, tagList`) — `author`, `favorited` and `favoritesCount` are composed in the
monolith from the User/Favorite ports on both paths and are not part of the comparison. Watch
especially `articlesCount`, `hasNext` and the `DateTimeCursor` millis on paged endpoints, and the
`tagList` order (which is why `tag` is reconciled before `article`).

Exit criterion: ≥ 99.99 % agreement over ≥ 24 h with every mismatch explained (typically an
in-flight dual-write). Keep hourly reconciliation running.

## 5. Enter state B — `read=extracted`

```sh
EXTRACTION_ARTICLE_READ=extracted <restart monolith>   # fallback stays 'monolith'
```

Verify:

```sh
curl -s 'localhost:8080/articles?limit=5' | jq '.articlesCount, [.articles[].slug]'   # same as before the flip
curl -s localhost:8080/articles/<slug> | jq '.article | {slug, tagList, favoritesCount, author}'  # identical
curl -s 'localhost:8080/articles?author=<username>' | jq '.articlesCount'            # same as before
curl -s 'localhost:8080/articles?author=nobody-here' | jq '.articlesCount'           # 0, articles: []
curl -s -H "Authorization: Token $JWT" localhost:8080/articles/feed | jq '.articlesCount'
curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/articles/does-not-exist       # 404
curl -s -X POST -H "Authorization: Token $JWT" -H 'Content-Type: application/json' \
  -d '{"article":{"title":"<existing title>","description":"d","body":"b"}}' localhost:8080/articles  # 422 article name exists
favorite-sync reconcile --domain tag     --source dev.db --target article-service/article.db; echo tag=$?       # 0
favorite-sync reconcile --domain article --source dev.db --target article-service/article.db; echo article=$?   # 0
```

An article with no tags must still return `"tagList": []`, never `null`. Stop the service briefly
and confirm `GET /articles/{slug}` and `GET /articles` still return 200 served by the fallback
(`extraction.article.fallback=monolith`). Restart the service.

**Rollback from A/A'/B is a single flag** (05 §6.1, phase-4 §6.1): `EXTRACTION_ARTICLE_ENABLED=false`
(or `EXTRACTION_ARTICLE_READ=monolith` to keep dual-write warm). No data work is needed — every
write landed in `dev.db` first. **Article:** with the Article flag off, Phase 3's own tag
dual-write on article create is active again (phase-4 §2.1), so `--domain tag` stays clean.

## 6. Cutover to state C — service authoritative (05 §5.2, §5.3)

Entry criteria: N days of `CLEAN` on both domains (step 3), zero dead-lettered outbox rows, the
rollback drill (§8) executed once in a non-production environment, an owner on call.

```sh
favorite-sync reconcile --domain tag     --source dev.db --target article-service/article.db; echo tag=$?       # must be 0
favorite-sync reconcile --domain article --source dev.db --target article-service/article.db; echo article=$?   # must be 0 right before the flip
EXTRACTION_ARTICLE_WRITE=extracted <restart monolith>
date -u +%Y-%m-%dT%H:%M:%SZ   # record T_flip
```

From now on article writes (and the tags they carry) go only to the service; `dev.db`'s `articles`
becomes a read-replica kept warm by the reverse repair below. **Comments and favorites are still
written by their own Phase 1/2 seams** and keep storing the `article_id` the service issued — the
UUID is generated by the monolith's `Article` before the remote call, so it is the same value on
every side. Continue hourly reconciliation, now labelled:

```sh
favorite-sync reconcile --domain article --source dev.db --target article-service/article.db --authoritative service \
  --report build/reconcile/article/$(date -u +%Y%m%dT%H%M%SZ).json
```

With `--authoritative service` the interesting buckets are `extraInService` (= rows the monolith
replica is missing), `missingInService` (= articles deleted in the service, still in the replica)
and `diverged`. To keep the replica warm, run periodically (tag first):

```sh
favorite-sync reconcile --domain tag     --source dev.db --target article-service/article.db --authoritative service --repair to-source
favorite-sync reconcile --domain article --source dev.db --target article-service/article.db --authoritative service --repair to-source
```

**Article:** without `--delete-extras` the replica keeps articles that were deleted in state C.
Their slugs stay occupied in `dev.db`, so a later article that re-uses the title will be reported
as `uniqueConflictsInMonolith` and skipped by the reverse repair. Either accept the service's view
periodically (`--repair to-source --delete-extras`, which deletes replica-only `articles` rows and
nothing else) or resolve the listed ids by hand before a rollback.

The monolith tables are dropped only after ≥ 30 days without rollback, via a new Flyway migration —
`articles` together with `tags`/`article_tags`, since `ArticleReadService.xml` joins all three
whenever `extraction.article.enabled=false`. Separate approval.

## 7. Rollback from state C (05 §6.2, phase-4 §6.2)

1. Pause article writes for the flip duration if possible (an article created between the flip
   and the reverse-backfill is still recovered by step 3).
2. Flip back to monolith-first:
   ```sh
   EXTRACTION_ARTICLE_WRITE=dual-write EXTRACTION_ARTICLE_READ=monolith <restart monolith>
   ```
   (or `EXTRACTION_ARTICLE_ENABLED=false` to go fully local; `dual-write` keeps a retry cheap).
3. Reverse-backfill the authority-flip window, **tag first** (tags written inside
   `POST /internal/articles` never reached `dev.db` either), then article — copies every row that
   exists only in the service into the monolith by `id`, leaving monolith rows untouched:
   ```sh
   favorite-sync reverse-backfill --domain tag     --source dev.db --target article-service/article.db \
     | tee build/reconcile/tag/reverse-backfill.log
   favorite-sync reverse-backfill --domain article --source dev.db --target article-service/article.db \
     | tee build/reconcile/article/reverse-backfill.log; echo exit=$?
   ```
   Expected:
   ```
   reverse-backfill: copying article-service/article.db -> dev.db
   backfill domain=article table=articles source=article-service/article.db target=dev.db chunk=5000
   backfill done rowsRead=1231 rowsInserted=24 rowsSkipped=1207 chunks=1 targetRowsAfter=1231 T0=... table=articles
   exit=0
   ```
   `rowsInserted` is the size of the window that the reverse repair had not delivered.
   **Article:** `exit=1` with `backfill conflict table=articles <service id> slug=<s> held by
   <monolith id>` means a state-C article re-used the title of an article that was deleted in the
   service but still sits in the replica (see §6). Resolve **by id first** (phase-4 §6.2): the
   monolith copy is stale, so delete it — step 4's `--repair to-source --delete-extras` does
   exactly that, then re-run the reverse-backfill (idempotent) so the new article lands.
4. Verify: zero extra-in-service and zero diverged.
   ```sh
   favorite-sync reconcile --domain article --source dev.db --target article-service/article.db --authoritative service \
     --report build/reconcile/article/rollback-$(date -u +%Y%m%dT%H%M%SZ).json; echo exit=$?
   ```
   Expected: `extra=0 diverged=0 conflicts=0/0`. `missing>0` means the replica holds articles the
   service deleted in state C; the service's view is the truth for the window, so apply it:
   `--repair to-source --delete-extras` (with `--authoritative service` this deletes the
   monolith-only `articles` rows — their comments/favorites/tag pairs stay, exactly as a monolith
   delete would have left them). `diverged>0` here is a defect in the service's persistence of the
   window's rows; `--repair to-source` overwrites the monolith copy from the service. Then run the
   same check for `--domain tag`.
5. Because there are no FK constraints (05 §1.2, phase-4 §6.3) nothing else in `dev.db`,
   `comment.db` or `favorite.db` is affected: comments and favorites written during state C still
   reference the article ids that were just copied back, and `article_tags` pairs of the window
   arrived in step 3. Re-populating `articles` never changes an id.
6. Sanity-check the user-visible reads with the flag off:
   ```sh
   EXTRACTION_ARTICLE_ENABLED=false <restart monolith>
   curl -s localhost:8080/articles/<slug-created-in-state-C> | jq '.article | {slug, tagList, favoritesCount}'
   curl -s localhost:8080/articles/<slug-created-in-state-C>/comments | jq '.comments | length'
   curl -s 'localhost:8080/articles?limit=1' | jq '.articlesCount'
   ```
   `favoritesCount` and the comments of a state-C article must be exactly what the service showed
   before the rollback.

## 8. Rollback drill (05 §6.4) — run once per environment before step 6

Use copies of the databases, never production files.

```sh
cp dev.db drill-dev.db && cp article-service/article.db drill-article.db
```

| # | Action | Command / flag | Assert |
|---|---|---|---|
| 1 | Reach state B | steps 1, 2, 3, 5 above on the drill DBs | `reconcile --domain tag ...; reconcile --domain article ...` → both `exit=0` |
| 2 | Kill the service mid-traffic; create, update and delete articles | `kill <article-service pid>`; `curl -X POST/PUT/DELETE .../articles...` | every request 2xx; rows present/changed/gone in `drill-dev.db` |
| 3 | Restart the service, let the outbox drain | — | `favorite-sync reconcile --domain article --source drill-dev.db --target drill-article.db` → `status=CLEAN`, `exit=0` (use `--repair to-target --delete-extras` once if the outbox dead-lettered a delete) |
| 4 | Flip to state C and generate writes | `EXTRACTION_ARTICLE_WRITE=extracted`; create two articles (one with a brand-new tag), update one, delete a pre-existing one, comment on and favorite a new one | `reconcile --domain article ... --authoritative service` shows `extra=2 missing=1`; `--domain tag` shows `extra>0` |
| 5 | **Article:** provoke a slug conflict | in state C create an article with the exact title of the article deleted in step 4 | `reverse-backfill --domain article` in step 6 prints `backfill conflict ... held by <deleted id>` and exits `1` |
| 6 | Execute §7 | `EXTRACTION_ARTICLE_WRITE=dual-write`; `reverse-backfill --domain tag`, then `--domain article` on the drill DBs | `rowsInserted` on `articles` = 2 (the conflicting one skipped) |
| 7 | Resolve by id | `favorite-sync reconcile --domain article --source drill-dev.db --target drill-article.db --authoritative service --repair to-source --delete-extras`; re-run `reverse-backfill --domain article` | deleted replica row gone, conflicting article inserted, `rowsInserted=1` |
| 8 | Verify | `favorite-sync reconcile --domain article --source drill-dev.db --target drill-article.db --authoritative service; echo exit=$?` | `extra=0 diverged=0 conflicts=0/0`, `exit=0`; same for `--domain tag` |
| 9 | **Article:** read round-trip with the flag off | `EXTRACTION_ARTICLE_ENABLED=false`; `curl localhost:8080/articles/<slug from step 4>` and `.../comments` | `tagList`, `favoritesCount`, `updatedAt` and comments identical to what the service returned in state C |
| 10 | Idempotency | run steps 6 and 8 a second time | `rowsInserted=0`, `exit=0` |

Record the ten results (with the JSON reports) in the change ticket; this is entry criterion 3 of
05 §5.2.

| Situation | Command |

| Hourly drift check (alert on exit 1) | `favorite-sync reconcile --domain tag --source dev.db --target article-service/article.db --report build/reconcile/tag/$(date -u +%Y%m%dT%H%M%SZ).json && favorite-sync reconcile --domain article --source dev.db --target article-service/article.db --report build/reconcile/article/$(date -u +%Y%m%dT%H%M%SZ).json` |
| Service missing rows or a diverged article (states A/B) | `favorite-sync reconcile --domain article --source dev.db --target article-service/article.db --repair to-target` |
| Service has rows the monolith does not, or a slug held by a service-only id (states A/B) | `favorite-sync reconcile --domain article --source dev.db --target article-service/article.db --repair to-target --delete-extras` |
| Slug held by an id that exists on both sides | resolve by id by hand (delete or re-title one article through the monolith), then re-run reconcile — never auto-repaired |
| Rebuild service DB from scratch (states A/B) | stop service, delete `article-service/article.db`, start service (Flyway), `favorite-sync backfill --domain tag ...`, `favorite-sync backfill --domain article ...`, then both `reconcile`s |
| Rollback from A/A'/B | `EXTRACTION_ARTICLE_ENABLED=false` — no data work |
| Rollback from C | `EXTRACTION_ARTICLE_WRITE=dual-write EXTRACTION_ARTICLE_READ=monolith`, `reverse-backfill --domain tag`, `reverse-backfill --domain article`, `reconcile --domain article ... --authoritative service [--repair to-source --delete-extras]` — §7 |
| Keep the monolith replica warm in state C | `favorite-sync reconcile --domain article --source dev.db --target article-service/article.db --authoritative service --repair to-source` |
| Comments/favorites of a moved or deleted article | nothing — they reference `article_id` by value, no FK, no cascade on either side |
